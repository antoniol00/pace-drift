# Methodology

Technical detail of the critical design decisions. The README gives the overview; this document is the reference for anyone auditing the protocol.

## 1. Shared drift schedule

**Problem.** With per-phase dynamic detection, the moment a phase modifies its model, its error signal diverges from the other phases' and PHT fires at different indices. B and C then respond to *different events*, and per-event comparisons (RT, AUD, Wilcoxon pairing) are meaningless.

**Design.**

- *Primary schedule* (`build_schedule_from_pht`): a "pass 0" runs the reactive baseline's dynamics (HAT + dynamic PHT + training windows) once per dataset, at seed 0, and records the fire indices. Every scheduled arm (`B`, `ARF_sched`, `SRP_sched`) replays these indices via `ScheduledDriftTrigger`, for every seed and every learner. The schedule is biased toward the baseline's dynamics by construction; this is acceptable because that baseline is the reference the proposal must beat, and the alternative (per-arm detection) breaks pairing entirely. Because the ensembles replay HAT's schedule, and `B` at seeds 1–9 replays the seed-0 run's, while the error test inside `*_early` watches each run's own error, `B_pht` / `ARF_pht` / `SRP_pht` run that error PHT live on the learner with no monitor, so `*_early − *_pht` isolates the monitor.
- *Adaptation windows*: a firing opens `train_window = 5,000` samples, learned from the firing sample on; a firing inside an open window restarts it (no stacking). The labelled share of the evaluated stream is therefore the union of the windows (`metrics/cost.py:labelled_samples`) and is reported beside every firing count. Pretraining (50,000 labelled samples) is identical in every arm and excluded from metrics and label shares. The error PHT is river's default (λ = 50, 30 min instances, α = 0.9999, two-sided) at δ = 0.002; the recon PHT is two-sided with 10 min instances, so the monitor fires at most once every 10,000 samples. The two PHTs are independent (a firing of one does not reset the other).
- *Complementary schedule* (`build_schedule_from_labels`): ground truth derived from label transitions. An event is recorded at the first sample of each new non-BENIGN subtype block; consecutive events closer than `min_gap` are merged (first kept). Events inside the pre-training prefix are dropped. This schedule is model-free but "oracle" (uses labels the deployed system would not have); we use it for sensitivity analysis, not headline results.
- When a schedule is active, a PHT still runs in **report-only** mode (`report_pht_indices`): its fires measure how much later error-based detection would have triggered relative to the scheduled events, but never cause adaptation.
- Index convention: indices count samples of the evaluated stream starting at 1 for the first sample after `start_row`, pre-training included. A scheduled index that the stream never reaches (filtered row) is dropped, never fired late — adaptation timing must not depend on phase dynamics.
- **The proactive arms are exempt**: their claimed contribution is anticipation, which a fixed schedule would erase. They always run dynamic dual detection, and their recovery metrics are compared with the caveat that their events differ (stated explicitly in any report).

## 2. Recovery metrics

Definitions over rolling-F1 snapshots taken every `snap_interval` samples (window = 5,000; snapshots start after 100 window samples).

- **Validity.** A snapshot is *invalid* when its rolling window contains no positive (ATTACK) true label: F1 is undefined there (the old notebooks plotted it as 0, silently corrupting recovery measurements). Invalid snapshots are **excluded** from RT and AUD — they neither break nor extend a sustained run — and their fraction is reported per event (`excluded_windows_pct`).
- **Drift indices.** Each run's own adaptation firings: the shared schedule for scheduled arms, the arm's own firings (either test) for live arms. No label-derived ground truth enters RT/AUD. The per-event stratification (`scripts/review_checks.py` section C) restricts to PACE's error-test firings.
- **Event window.** From drift index `d` to `min(d + H, next_drift)`, with `H = 50,000` by default.
- **RT**: samples from `d` to the *first* snapshot of the first run of `k = 3` consecutive valid snapshots with `F1 >= theta` (`theta = 0.9`). A tail run cut short by the event window end does not count (the "sustained" requirement is not met inside the window).
- **AUD**: `sum over valid snapshots i of max(0, theta - F1_i) * (idx_i - idx_{i-1})`, rectangle rule with `idx_0 = d`, up to the recovery snapshot, or to the last valid snapshot of the event window when there is no recovery. Units: deficit × samples. The step is the spacing between consecutive **valid** snapshots and is **not** capped at `snap_interval`, so a deficit seen after an excluded benign-only stretch is attributed to the whole stretch — one reason AUD only appears in the secondary per-event analysis.
- **Benign-window blind spot.** A window with no attack but with false positives has a well-defined F1 of 0, yet the validity rule excludes it, so local F1 cannot see false-positive storms inside benign-only stretches (36% of windows on CIC-IDS2017/2018, none on UNSW-NB15). Always pair local F1 with the whole-stream benign FPR and cumulative accuracy. `review_checks.py` section A re-derives the headline contrasts with those windows scored 0 ("strict" F1); note that metric's cliff (one FP → F1 0) magnifies differences of a few flows.
- **Overlap.** If the next drift arrives before recovery, the current event closes with `no_recovery = True` and a new event opens. Events are therefore disjoint and each sample of deficit is attributed to exactly one event.
- **Aggregation.** RT statistics are computed over recovered events only, and are always reported next to `no_recovery_rate` — comparing RT between phases with different no-recovery rates is survivorship bias, and the reporting code keeps both visible.

## 3. Multi-seed protocol and statistics

- Seeds: `random`, `numpy` (global + local `default_rng`), `torch` CPU/CUDA, the base learner (`seed=` at construction). Real-data results use 10 seeds; the comparator experiment uses 20, because its collapse outcome is bimodal and a handful of replicates estimates a bimodal rate badly.
- Every run writes `manifest.json`: git commit, SHA-256 of the input CSV (cached by size+mtime), fully resolved config + hash, seed, package versions, timestamp.
- Point estimates: mean ± 95% CI via percentile bootstrap (10,000 resamples) — no normality assumption.
- Nine-cell aggregates are reported over cell means **and** by a hierarchical bootstrap (resample datasets, then seeds within each cell), because the three learners of a dataset share its capture, monitor scores and schedule. With three datasets the hierarchical interval is conservative; the timing aggregate reaches zero under it ([−0.003, +0.084]). Do not use a sign test over the nine cells.
- Phase comparisons: Wilcoxon signed-rank **paired by `drift_index`** (valid only under the shared schedule; events missing in one phase are dropped from the pair set). Effect sizes: `r = |Z|/sqrt(n_pairs)` and Cliff's delta. With ~tens of events per run, p-values alone are not persuasive; effect sizes are primary.

## 4. The unsupervised covariate-shift trigger

- **Calibration provenance.** PACE's own recon threshold (0.1, δ 0.0005) was chosen once on the first 300K samples of the CIC-IDS2017 window at seed 0 (a prefix of the evaluated stream: mild lookahead on the anchor) and carried unchanged to 2018/UNSW after prefix smokes. The comparator monitors' thresholds and the `*_freq` intervals are calibrated on the **full** stream to match counts — hindsight settings by design, a control rather than a deployable configuration. Only the monitor's firings are matched; error-test firings are a consequence of the run (~107/run healthy, ~245/run collapsed on the 2017 HAT comparators).
- **D3 solver.** The logistic regression is fitted to convergence by L-BFGS (`scipy.optimize`, L2 1e-3, gtol 1e-6). The first comparator runs used a fixed 150-step gradient descent that left a median gradient norm of 0.44 on real flow buffers and flipped the AUC across 0.7 on 28/300 checks; those runs are kept under `results/runs_backup_d3_gd/` and superseded.
- Monitor: small autoencoder (in → 32 → 16 → 32 → in) fine-tuned every `monitor_interval = 1,000` samples for 5 epochs on a 2,000-sample buffer. The reconstruction error is measured against a **frozen reference scaler** (fixed on the first check) and **before** each fine-tune, so a covariate shift shows up as a *leading* spike; standardized inputs are clipped (`monitor_clip = 10`) to tame heavy-tailed features. This redesign replaced an earlier per-buffer standardization that cancelled the very signal being detected. Cheap ablations of this monitor (PCA / KS / MMD / mean-shift) share the identical protocol — see [experiments/02-monitor-ablation.md](experiments/02-monitor-ablation.md).
- `PHT_recon` (delta = 0.0005, threshold = 0.1, calibrated offline on the persisted recon-error series) over that signal; `PHT_class` (delta = 0.002) over the 0/1 error as usual. Either can trigger adaptation in a proactive arm; the fire source is recorded per event.
- **Lead time**: greedy one-to-one pairing of each class fire (in index order) with the nearest preceding unpaired recon fire within `lead_horizon = 20,000` samples; a recon fire at the same index is lead 0, so leads are non-negative by construction and a late monitor shows up as low recall. Missed-anticipation rate = 1 − recall. A successful early window can suppress the class fire it anticipated (counted as a false alarm); pairing the same recon fires against the live control's (`*_pht`) class fires, which no monitor window pre-empts, gives the same recall / false-alarm / lead in every cell (`review_checks.py` section B). Reported: mean/distribution of lead times, anticipated-FP rate (recon fires never followed by a class fire within the horizon), missed-anticipation rate (class fires with no preceding recon fire).
- Falsifiability: the hypothesis fails if lead times are ~0/negative-dominated or the anticipated-FP rate makes early adaptation more costly than the lead time is worth. The analysis reports whichever outcome the data supports.
- **Per-dataset recalibration (external validity, #4).** The recon Page-Hinkley threshold is calibrated per dataset because the reconstruction-error scale differs across feature spaces. The offline rule is the same: run the monitor over a smoke window, inspect the recon-error series and fire behaviour, and pick the threshold so the monitor fires on real bursts rather than every window. For CIC-IDS2018 and UNSW-NB15 the 2017 value (`0.1`, delta `0.0005`) was confirmed to generalize (2018: 185 fires / mean lead ~3.2K over a 1M smoke; UNSW: 25 fires / mean lead ~6.3K over a 200K smoke); the values are pinned in `configs/datasets/<name>.yaml` so every proactive arm on a dataset shares the same calibrated monitor. Values that depend on the *(dataset, phase)* pair rather than the dataset alone — the blind clock's interval, calibrated per learner — go in that profile's `by_phase:` block. `scripts/calibrate_monitor.py` performs the sweep offline against a cached score series.

## 5. Security evaluation: adversary and defence

- **Oracle adversary** (`adversary_schedule`): fires the monitor branch at precomputed indices instead of running a monitor, under the monitor's constraints (monitor check points only, ≥ `recon_pht_min_instances` checks apart, at most PACE's mean monitor firings). `scripts/adversary_schedule.py` builds the *attack* goal (windows ≥ 50% attack, highest first: 31 firings at 0.949) and the *benign* goal (54 attack-free windows) from the labels of a stored trace.
- **Chaff** (`chaff_schedule`, `chaff_size`, `chaff_pool`): `data/stream.py:inject_chaff` inserts benign-labelled flows (raw label `CHAFF`) whose every feature is copied from a different benign flow of the first `chaff_pool` benign flows. Chaff is classified, feeds both tests and is learned from inside windows, but is excluded from rolling F1, accuracy, snapshots, traces and the stream index, so every arm is scored on the same real flows.
- **Window rebalancing** (`rebalance_prior`, `replay_size`): `models/rebalance.py:WindowRebalancer` keeps per-class reservoirs (Algorithm R) of every labelled flow the learner sees; after each flow learned in a window it replays flows of the under-represented class until the window's attack share is in `(prior − 1/n, prior]`; counts reset on every firing. The anchor's prior is the pretraining attack share (0.134). `summary.json:learned` records what the learner was fed, replays separately.

## 6. Cost accounting

- Per-sample latency measured with `time.perf_counter()` around the full processing of each evaluated sample; reported p50/p95/p99/max.
- Component breakdown: `hat_inference`, `hat_update`, `monitor`, `other` (sample time not covered by a section).
- RSS sampled every 5,000 samples via psutil; peak and mean reported.
- Trade-off view: Pareto scatter of mean RT vs p95 latency, one point per (phase, seed).
